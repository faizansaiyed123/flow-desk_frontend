# FlowDesk — Visual Full-Stack Test Walkthrough

FlowDesk is a multi-tenant workspace for managing clients, projects, tasks, work time, invoices, team access, API keys, and webhooks. This guide follows user journeys through the React application and explains how browser actions are checked against the FastAPI API and PostgreSQL.

> **Verification status:** <!-- LATEST_FULL_STACK_RUN -->[All required checks passed](https://github.com/faizansaiyed123/flow-desk_frontend/actions/runs/40157195979).<!-- /LATEST_FULL_STACK_RUN -->
>
> The screenshots linked below are generated by Playwright in a real Chromium browser. The full-stack workflow starts PostgreSQL, applies Alembic migrations, starts FastAPI and Vite, runs the browser and API suites, and checks that expected rows are persisted. Screenshots are not copied from the reference project, mocked, or drawn.

## The product at a glance

**Register → dashboard → client → project → task board → time entry → invoice → team invitation → API key and webhook → search and notifications**

**Request path:** User in Chromium → React + TypeScript → Vite proxy for /api → FastAPI → authentication and tenant scope → validation and business services → SQLAlchemy → PostgreSQL → JSON response → rendered UI.

The browser test does not register mocked API responses. Vite forwards /api requests to the backend on port 8000, and CI runs against an isolated PostgreSQL database.

## How to read the evidence

For the complete list of registered API methods/paths, backend test modules, frontend workflow mapping, and explicitly unverified integration gaps, see the [endpoint-by-endpoint coverage inventory](ENDPOINT-COVERAGE.md).

Each walkthrough screenshot is a genuine full-page screenshot produced by Playwright while it performs that step. The browser test waits for corresponding HTTP responses and checks their status and important response values. After the UI flow, a separate read-only script queries PostgreSQL for the workspace, client, project, task, time entry, invoice, invitation, API key, and webhook records.

The checklist uses three states:

- **Pending** — planned but not yet verified by a successful CI run.
- **Pass** — the corresponding test completed successfully.
- **Gap / API-only** — the backend capability is tested at the API/data layer, but the UI does not expose a user workflow for it.

Do not treat a screenshot alone as proof that data persisted. For state-changing journeys, use the API response assertions and the direct PostgreSQL checks together.

## 1. Signing in and account recovery

### Login

![FlowDesk login page](visuals/00-login.png)

Open /login. The screen accepts an account email and password. Authentication is handled by the FastAPI auth endpoint, and the client stores the returned token pair in its auth store.

**Checks:** login renders; protected-route redirects, invalid credentials, registration, logout, and session reload are covered by the existing Playwright authentication suite.

### Request a password-reset email

![Password reset request](visuals/00-forgot-password.png)

Choose **Forgot password?**, enter an email address, and submit. The backend returns a generic confirmation so the page does not disclose whether a particular account exists. With email delivery disabled in the isolated test environment, this verifies the real API request and response, not delivery to an external mailbox.

### Missing and invalid reset tokens

![Reset page without a token](visuals/00-missing-reset-token.png)

A reset URL without a token keeps the action disabled. An unknown token is submitted to the real reset endpoint and must return an HTTP client error rather than changing a password.

![Invalid password reset link](visuals/00-invalid-reset-link.png)

### Complete password reset and log in with the new password

![Valid password-reset token](visuals/24-valid-reset-token.png)

The walkthrough requests a reset for the registered account and follows the real reset URL written by the disposable backend's development-mode mailer. External SMTP is disabled; reset tokens are not included in screenshots or uploaded logs.

![Password reset succeeded](visuals/25-password-reset-success.png)

Submitting the new password must produce a successful POST /api/v1/auth/reset-password response and return the browser to the login page.

![Successful login after password reset](visuals/26-login-after-reset.png)

The test then logs in with the new password, verifies a real POST /api/v1/auth/login response containing an access token, and confirms the dashboard is reachable. This proves the password update affected authentication rather than only the form state.

### Invitation links

![Invitation page without a token](visuals/00-missing-invitation-token.png)

An invitation without a token is rejected in the UI. An unknown token is sent to the public invitation-preview API and returns an error state.

![Invalid invitation link](visuals/00-invalid-invitation.png)

### Register a workspace

![Workspace registration form](visuals/00-register.png)

Enter a name, workspace, email, and password that meets the validation rules, then choose **Create workspace**. The browser asserts that the real POST /api/v1/auth/register request succeeds and returns an access token.

The test uses a freshly created workspace and a run-specific email. It does not seed a fake signed-in frontend state.

### Workspace dashboard

![FlowDesk workspace dashboard](visuals/01-dashboard.png)

After registration, FlowDesk opens **Overview**. Dashboard counts and the revenue chart come from GET /api/v1/dashboard/summary; empty states are expected when a new workspace has no projects, tasks, or invoices.

## 4. Time tracking

### Log time manually

![Manual time entry](visuals/08-time-tracking-manual-entry.png)

From **Time**, choose **Log time manually**, select the project, enter a date and time, set the duration to 45 minutes, and add a description. The test asserts that POST /api/v1/time-entries succeeds and returns the requested duration.

The Time page now exposes an edit action for each unbilled entry. The walkthrough changes the description using the visible edit dialog, asserts PATCH /api/v1/time-entries/{entry_id} returns the updated value, and the direct PostgreSQL check verifies the edited description and 45-minute duration. Invoiced entries remain non-editable, consistent with the backend rule.

![Temporary time entry deleted](visuals/08b-time-entry-deleted.png)

A second, disposable 15-minute manual entry is deleted through its row action. The test asserts DELETE /api/v1/time-entries/{entry_id}, verifies that the row disappears, and confirms in PostgreSQL that the temporary entry no longer exists.

### Start and stop the running timer

![Running timer](visuals/09-time-tracking-running.png)

Choose the project and select **Start timer**. The backend creates a real time-entry row with a start time and no end time. The screen then offers **Stop**.

![Timer stopped and entry reloaded](visuals/10-time-tracking-stopped-reloaded.png)

Select **Stop**. The test verifies that the timer-stop response has an end timestamp, reloads the page, and confirms the manual entry remains visible. PostgreSQL verification checks the manual entry's project, description, and duration.

### Generate an invoice from billable time

![Invoice generated from unbilled time](visuals/10b-invoice-from-time-generated.png)

After stopping the timer, choose **Invoice unbilled time**. The walkthrough opens the generated invoice and checks the server-returned state.

## 10. Reproduce the full-stack test locally

Use a disposable PostgreSQL database. Do not point these test commands at a production database.

1. Create separate databases named flowdesk_test for backend tests and flowdesk_e2e for the browser run.
2. From the backend repository, install requirements-dev.txt, configure DATABASE_URL and a non-production SECRET_KEY, then run pytest -q.
3. Point the backend to flowdesk_e2e, apply alembic upgrade head, and start FastAPI at http://localhost:8000.
4. From the frontend repository, run npm ci, npm run lint, npm run build, npm test, and npx playwright install chromium.
5. Run npm run e2e. Playwright starts Vite at http://localhost:5173; the /api proxy forwards to port 8000.
6. Run python e2e/verify-postgres-state.py from the frontend repository with DATABASE_URL set to the same disposable flowdesk_e2e PostgreSQL database. This script performs read-only checks on records made by the visual journey.

For CI, use the check-run link above and download the flowdesk-full-stack-test-evidence artifact for the HTML Playwright report, failure screenshots/traces, and backend log.
