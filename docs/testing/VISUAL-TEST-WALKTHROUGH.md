# FlowDesk — Visual Full-Stack Test Walkthrough

FlowDesk is a multi-tenant workspace for managing clients, projects, tasks, work time, invoices, team access, API keys, and webhooks. This guide follows user journeys through the React application and explains how browser actions are checked against the FastAPI API and PostgreSQL.

> **Verification status:** <!-- LATEST_FULL_STACK_RUN -->Pending first successful full-stack CI run.<!-- /LATEST_FULL_STACK_RUN -->
>
> The screenshots linked below are generated by Playwright in a real Chromium browser. The full-stack workflow starts PostgreSQL, applies Alembic migrations, starts FastAPI and Vite, runs the browser and API suites, and checks that expected rows are persisted. Screenshots are not copied from the reference project, mocked, or drawn.

## The product at a glance

**Register → dashboard → client → project → task board → time entry → invoice → team invitation → API key and webhook → search and notifications**

**Request path:** User in Chromium → React + TypeScript → Vite proxy for /api → FastAPI → authentication and tenant scope → validation and business services → SQLAlchemy → PostgreSQL → JSON response → rendered UI.

The browser test does not register mocked API responses. Vite forwards /api requests to the backend on port 8000, and CI runs against an isolated PostgreSQL database.

## How to read the evidence

Each walkthrough screenshot is a genuine full-page screenshot produced by Playwright while it performs that step. The browser test waits for corresponding HTTP responses and checks their status and important response values. After the UI flow, a separate read-only script queries PostgreSQL for the workspace, client, project, task, time entry, invoice, invitation, API key, and webhook records.

The checklist uses three states:

- **Pending** — planned but not yet verified by a successful CI run.
- **Pass** — the corresponding test completed successfully.
- **Gap / API-only** — the backend capability exists and is tested at the API/data layer, but the current frontend does not expose a user workflow for it.

Do not treat a screenshot alone as proof that data persisted. For state-changing journeys, use the API response assertions and the direct PostgreSQL checks together.

## 1. Signing in and account recovery

### Login

![FlowDesk login page](visuals/00-login.png)

Open /login. The screen accepts an account email and password. Authentication is handled by the FastAPI auth endpoint, and the client stores the returned token pair in its auth store.

**Checks:** login renders; protected-route redirects, invalid credentials, registration, logout, and session reload are covered by the existing Playwright authentication suite.

### Request a password-reset email

![Password reset request](visuals/00-forgot-password.png)

Choose **Forgot password?**, enter an email address, and submit. The backend returns a generic confirmation so the page does not disclose whether a particular account exists. With email delivery disabled in the isolated test environment, this verifies the real API request and response, not delivery to an external mailbox.

### Missing and invalid reset tokens

![Invalid password reset link](visuals/00-invalid-reset-link.png)

A reset URL without a token keeps the action disabled. An unknown token is submitted to the real reset endpoint and must return an HTTP client error rather than changing a password.

### Invitation links

![Invalid invitation link](visuals/00-invalid-invitation.png)

An invitation without a token is rejected in the UI. An unknown token is sent to the public invitation-preview API and returns an error state. The backend suite separately tests invitation creation and acceptance rules; a complete valid invitation-acceptance browser journey remains a separate item in the checklist.

### Register a workspace

![Workspace registration form](visuals/00-register.png)

Enter a name, workspace, email, and password that meets the validation rules, then choose **Create workspace**. The browser asserts that the real POST /api/v1/auth/register request succeeds and returns an access token.

The test uses a freshly created workspace and a run-specific email. It does not seed a fake signed-in frontend state.

### Workspace dashboard

![FlowDesk workspace dashboard](visuals/01-dashboard.png)

After registration, FlowDesk opens **Overview**. Dashboard counts and the revenue chart come from GET /api/v1/dashboard/summary; empty states are expected when a new workspace has no projects, tasks, or invoices.

## 2. Managing clients

### Create and list a client

![Client directory](visuals/02-clients-list.png)

Open **Clients → New client** and enter a name, company, and email. The test checks the actual POST /api/v1/clients response and confirms that the created client appears in the list.

### Open, update, and reload the client record

![Client details](visuals/03-client-detail.png)

Open the client, add a note, and save. The test verifies the real PATCH /api/v1/clients/{client_id} response, reloads the page, and checks that the note is returned again by the client detail API.

![Client after saved changes](visuals/03-client-detail-updated.png)

The reload distinguishes data read back from the backend from text that only remains in local form state.

**Additional client checks in the existing E2E suite:** empty state, required-name validation, list search, archive/unarchive, delete, and the detail route.

## 3. Projects and the Kanban task board

### Create a project

![Projects directory](visuals/04-projects-list.png)

Go to **Projects → New project**, enter a name, and save. The browser asserts a successful POST /api/v1/projects response and confirms the project is listed.

### Create a task in the board

![Project task board](visuals/05-project-kanban.png)

Open the project and add a task to **Backlog**. The test verifies the actual POST /api/v1/tasks response and retains the task ID for subsequent checks.

### Move a task to In Progress

![Task detail with In Progress status](visuals/06-task-detail-in-progress.png)

Open the task and change **Status** to **In Progress**. The real task-update endpoint must return the in_progress state.

![Task after reloading the project](visuals/06-task-status-reloaded.png)

The browser reloads the project after the status change. The CI database verification separately checks that the task row contains the new status for the current workspace.

The existing project/Kanban suite adds coverage for project status filters, task title editing, task detail, and comments. The backend suite tests status filtering, task ordering, completion timestamps, moving tasks, validation, comment creation/listing, and deletion.

## 4. Time tracking

### Log time manually

![Manual time entry](visuals/07-time-tracking-manual-entry.png)

From **Time**, choose **Log time manually**, select the project, enter a date and time, set the duration to 45 minutes, and add a description. The test asserts that POST /api/v1/time-entries succeeds and returns the requested duration.

### Start and stop the running timer

![Running timer](visuals/08-time-tracking-running.png)

Choose the project and select **Start timer**. The backend creates a real time-entry row with a start time and no end time. The screen then offers **Stop**.

![Timer stopped and entry reloaded](visuals/09-time-tracking-stopped-reloaded.png)

Select **Stop**. The test verifies that the timer-stop response has an end timestamp, reloads the page, and confirms the manual entry remains visible. PostgreSQL verification checks the manual entry's project, description, and duration.

## 5. Invoicing

### Create a draft invoice

![Draft invoice](visuals/10-invoice-draft.png)

Open **Invoices → New invoice**, select the client, and add two units of **Walkthrough implementation** at 50 per unit. The real invoice-create response must be in draft status with a calculated total of 100.

### Send the invoice

![Sent invoice](visuals/11-invoice-sent.png)

Select **Send**. The browser verifies the POST /api/v1/invoices/{invoice_id}/send response and the visible status transition to sent. The server validates the lifecycle; the UI does not merely relabel the invoice.

### Mark it paid and read it again

![Paid invoice after reload](visuals/12-invoice-paid-reloaded.png)

Select **Mark paid**, verify the API response, reload the invoice, and read its status from a fresh GET request. PostgreSQL verification checks the paid invoice row and its stored line item/amount.

The existing invoicing tests also exercise API validation and lifecycle behavior. The UI E2E suite includes the restriction that a sent invoice cannot be edited.

## 6. Workspace, team, and integrations

### Workspace settings

![Workspace settings](visuals/14-settings-workspace.png)

The Workspace tab reads the current tenant from the API. The walkthrough leaves the workspace name unchanged so the database assertions can identify the test tenant deterministically.

### Team invitation

![Pending team invitation](visuals/15-settings-team-invitation.png)

From **Settings → Team → Invite**, enter the invited email and submit. The test checks the real POST /api/v1/tenants/invitations response and the pending invitation displayed on the page.

### API key

![API key management](visuals/16-settings-api-keys.png)

Create an API key from **Settings → API Keys**. The actual API returns a one-time plaintext key, but the test deliberately does not print it or include it in a screenshot. After the dialog is dismissed, the list displays the key name/prefix and active status.

The database check verifies a key row exists with a stored hash. It does not expect the database to contain the plaintext secret.

### Webhook configuration

![Webhook configuration](visuals/17-settings-webhooks.png)

Open **Settings → Webhooks**, enter a target URL, select the task.created event, and save. The browser asserts a successful webhook-create response, and PostgreSQL verification confirms that the configuration exists and is active.

Webhook delivery is separate from configuration. Backend API tests exercise delivery logging and successful/failed outbound requests using controlled HTTP test doubles; those tests do not replace frontend/API responses in the browser walkthrough.

### Backend API coverage inventory

The backend registers these route groups under /api/v1: authentication; tenant/workspace and invitations; user profile; clients; projects; tasks and task comments; notifications; time entries and timer actions; invoices; webhooks and deliveries; API keys; attachments; activity; dashboard summary; and search. The backend test directory contains modules covering each of those major domain areas.

Not every backend endpoint currently has a corresponding screen or control in the frontend. Attachment operations have backend coverage but no visible attachment workflow in the app navigation/project detail; activity is fetched through a hook but has no dedicated route in src/App.tsx; and webhook update/delivery-history hooks are not exposed as controls in Settings. These are documented as integration gaps, not presented as complete click-through UI features.

## 9. Reproduce the full-stack test locally

Use a disposable PostgreSQL database. Do not point these test commands at a production database.

1. Create separate databases named flowdesk_test for backend tests and flowdesk_e2e for the browser run.
2. From the backend repository, install requirements-dev.txt, configure DATABASE_URL and a non-production SECRET_KEY, then run pytest -q.
3. Point the backend to flowdesk_e2e, apply alembic upgrade head, and start FastAPI at http://localhost:8000.
4. From the frontend repository, run npm ci, npm run lint, npm run build, npm test, and npx playwright install chromium.
5. Run npm run e2e. Playwright starts Vite at http://localhost:5173; the /api proxy forwards to port 8000.
6. Run python e2e/verify-postgres-state.py from the frontend repository with DATABASE_URL set to the same disposable flowdesk_e2e PostgreSQL database. This script performs read-only checks on records made by the visual journey.

For CI, use the check-run link above and download the flowdesk-full-stack-test-evidence artifact for the HTML Playwright report, failure screenshots/traces, and backend log.
